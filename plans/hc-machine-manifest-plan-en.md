# HC Machine Manifest — a structured index for tools and agents

Status: **approved; implementation in progress** (2026-07-05).

## 1. Why

The kit's machine-readable surface today is lopsided: `llms.txt` /
`llms-full.txt` (prose for LLM context, #345), the DTCG token JSON
(`./tokens/*` exports), and per-recipe `checks.json` — but **no
structured index of the kit itself**. Tools that want to *enumerate*
(generators, linters, IDE plugins, structured-output agents) have
nothing to consume; the public-API surface exists only as prose
(VERSIONING.md, docs pages) and as the road-to-1.0 audit's
*reproducible commands* (that plan's §6).

This plan productionizes those commands into build artifacts. The
manifest doubles as the **1.0 freeze list** the road-to-1.0 checklist
asks to publish.

## 2. Deliverables

1. **`manifest.json`** — generated by
   `packages/core/scripts/build-manifest.mjs` during the core build,
   emitted to `dist/manifest.json`, exported as
   `@hypermedia-components/core/manifest.json`, and served by the docs
   site at **`/api/manifest.json`** (a static Astro endpoint that
   re-serves the built file; `docs:build` already chains the core
   build first). Content, all mechanically extracted:
   - `version`, `generatedFrom` (git describe not available at pack
     time → package version only; **no timestamps**, output is
     deterministic and sorted),
   - `components[]`: block name, part classes, the `data-*` attribute
     surface that appears in the block's stylesheet, its token group
     (or `null`), its behavior (or `null`), docs path
     (`components/<slug>`),
   - `behaviors[]`: export name, `autoInit` (roster parsed from
     `behaviors.js`; `installChart` is the one opt-in),
   - `events[]`: every `hc:*` name with the source module (detail
     shapes stay on the docs pages — not reliably extractable),
   - `recipes[]`: name, purpose (the `Purpose:` line the CLI already
     parses), files, `needsBehavior` (from `checks.json` when it names
     one), docs path, contract path,
   - `macros[]`: tag name + attribute list,
   - `i18nKeys[]`, `exports[]` (the package export map keys).
2. **`custom-elements.json`** — a hand-written, spec-shaped Custom
   Elements Manifest for the two macros (`<hc-confirm-action>`:
   method/action/target/swap/variant/message/title/confirm-label/
   cancel-label/disabled-elt/indicator; `<hc-live-search>`:
   action/target/name/placeholder/label/aria-label/delay/submit-label
   — lists verified against the macro sources). Referenced from
   `package.json#customElements`, exported, and served at
   `/api/custom-elements.json`.
3. **Keystone test** (`packages/core/test/manifest.test.mjs`): builds
   the manifest in-process and asserts it against reality — every
   `hc-*.css` block is present, every `install*` export is claimed
   (component, recipe, or platform glue; an unmapped new export fails
   the build), the auto-init roster matches `behaviors.js`, recipes
   match the `recipes/` directory, macro attributes match the CEM.
   New API surface therefore cannot ship without the manifest
   learning about it.
4. **Docs**: `reference/manifest.mdx` (en + ja) — URLs, schema table,
   the determinism/CI guarantee, example `jq` queries; linked from the
   reference index. `llms.txt` gains `optionalLinks` to both JSON
   endpoints so prose-first agents can discover the structured data.

## 3. Non-goals

- **shadcn-compatible registry** — its files+deps model is built for
  copying framework source; our CLI already owns copying, and a
  second contract shape would drift. Not pursued.
- **CLI consumption of the manifest** — `listRecipes()` scans the
  directory the CLI itself bundles; that is its truth and works
  offline. Coupling the CLI to core's manifest would tie two release
  cycles together for no gain. The manifest is the *kit-level* index.
- Detail-shape schemas for events (docs pages own those), and
  versioned manifest history (the npm tarball per version is the
  history).
