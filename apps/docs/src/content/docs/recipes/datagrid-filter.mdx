Per-column filtering, spreadsheet-style, kept hypermedia: a filter
button in the header cell opens a
[filter-popover](/hypermedia-components/recipes/filter-popover/) shell
whose controls are namespaced **`f-<col>`**; **Apply** GETs the grid
URL with repeated `f-status=` params, and the server re-renders the
whole [datagrid](/hypermedia-components/components/datagrid/) filtered.
No client-side filtering: one round trip, zero state drift, and
print/export match the screen. Zero new JavaScript. Covered by the
[versioning policy](/hypermedia-components/reference/versioning/).

:::tip[Scaffold]
```sh
npx @hypermedia-components/cli add datagrid-filter
npx @hypermedia-components/cli validate page.html
```
Ships `recipe.html`, `expanded.html`, and the machine-checked
[server contract](https://github.com/ingcreators/hypermedia-components/blob/main/recipes/datagrid-filter/contract.md).
:::

## Live demo

Open **Filter** in the Status header, check a status or two, **Apply**
— the server answers only the matching rows, the trigger comes back
`data-filtered` (primary variant, `aria-label` naming the active
values), and the popover's checked states follow out of band. Uncheck
everything to see the absent-params branch bring the full list back.

## The markup

```html
<div class="hc-datagrid" id="items-grid">
  <!-- server-rendered: .hc-datagrid__scroll > table; the Status header
       cell holds the filter trigger -->
  <!--
  <th class="hc-datagrid__headcell" scope="col">
    Status
    <button class="hc-button" data-variant="ghost" data-size="sm"
            type="button" id="filter-status-trigger"
            popovertarget="filter-status-popover"
            aria-label="Filter Status">Filter</button>
  </th>
  -->
</div>

<div id="filter-status-popover" class="hc-popover" popover>
  <form id="filter-status-form" action="/items" method="get"
        data-hx-get="/items"
        data-hx-target="#items-grid"
        data-hc-close-popover-on-success>
    <fieldset class="hc-popover__body" id="filter-status-fields">
      <label class="hc-checkbox-label">
        <input class="hc-checkbox" type="checkbox" name="f-status" value="active">
        Active
      </label>
      <!-- …one checkbox per distinct value… -->
    </fieldset>
    <footer class="hc-popover__footer">
      <button class="hc-button" type="submit" data-variant="primary">Apply</button>
    </footer>
  </form>
</div>
```

The form is the filter-popover shell —
`data-hc-close-popover-on-success` (`installClosePopover()`,
auto-installed) dismisses it on any 2xx. Every control shares the
column's namespaced name (`f-status`), so Apply serializes repeated
`f-status=` params, and the form targets the **grid wrapper**
(`innerHTML` default) — the trigger's filtered state lives in the
header, so header and rows must change together.

## Server response contract

`GET /items?f-status=active&…`:

| Case | Response (200) |
| --- | --- |
| any `f-<col>` set | the grid fragment with only matching rows; the header trigger renders **`data-filtered`** with an `aria-label` naming the active values; plus an OOB `outerHTML` re-render of the form's **fieldset** with matching checked states (never the form — it carries `data-hc-close-popover-on-success` and must survive the request) |
| empty/absent `f-<col>` | the unfiltered grid — an all-unchecked Apply serializes no params, so it lands here; the trigger renders plain |
| unknown value | ignored (the server is the schema); nothing recognized falls back to unfiltered |

**Filters compose across columns**: each column's form carries the
*other* columns' active filters as server-rendered hidden `f-<col>`
inputs, so applying one filter preserves the rest. The querystring is
the whole filter state — name it with
[saved-views](/hypermedia-components/recipes/saved-views/) for
one-click recall, and page links keep their `f-<col>` params so
[paging](/hypermedia-components/recipes/datagrid-pager/) preserves the
filter.

## The applied-conditions bar

Column popovers are how a condition is **created**; they are a poor way
to find one again. In a wide grid the column may be scrolled out of
view, and plenty of conditions do not belong to a column at all — so the
response also renders an
[`hc-filterbar`](/hypermedia-components/components/filterbar/): the
read-out of the whole querystring, and its edit surface.

| Element | What the server renders |
| --- | --- |
| one `.hc-filterbar__item` per applied condition | in the order the user added them if you track it, otherwise column order |
| `__label` / `__op` / `__value` | the field's label, the operator, and the value **summarised** — `3 values` for a multi-value condition |
| the chip's `popovertarget` | an editor holding **only that condition**, pre-filled, submitting the same `f-<col>` names |
| `__remove` `href` | the current URL **minus that one param** |
| `__clear` `href` | the URL with no `f-` params — sort, columns and page size stay |

The bar rides with the grid fragment, so one response updates rows,
header triggers and bar together.

**Removing is navigation.** `__remove` and `__clear` are real links, so
dropping a condition works without JavaScript, is shareable, and
**Back puts it back**. Add `data-hx-get` to swap in place; the `href`
stays the no-JS path.

Every entry point writes the same params — the column popover, a chip's
editor and a hand-typed URL are three doors into one wire.

## Relative dates

A saved view is a stored querystring. Put an absolute date in it and the
view is **wrong tomorrow** — "shipping this week" saved on Monday means
last week by the following Monday, and time is what a large share of the
views a business actually saves are about.

So a condition value may be an **expression**, and the expression is
what gets stored:

```text
?f-ship-from=@week-start&f-ship-to=@week-end
?f-ordered-from=@today-7d
```

`@today`, `@week-start` / `@week-end`, `@month-start` / `@month-end`,
`@quarter-*`, `@year-*`, and offsets from any anchor —
`@today-7d`, `@month-start-1m` (`d` / `w` / `m` / `y`).

**The server resolves, never the client.** Resolving in the browser puts
the browser's clock and timezone into the answer, and two colleagues
opening the same view would see different rows. Resolve every condition
in a request against **one** instant, or a request made near midnight
can straddle two days.

**Absolute values stay ISO** — `2026-08-01`, never `01/08/2026`. A
locale-formatted date in a stored view means different days to different
colleagues; localize on the way *out* with
[`<time data-hc-time>`](/hypermedia-components/fundamentals/i18n/), never
on the wire.

**The bar shows both forms:**

```html
<span class="hc-filterbar__value">start of this week (2026-08-10)</span>
```

Either alone leaves the condition a guess — the wording without the date
hides which rows are in; the date without the wording hides that it will
move tomorrow.

### Entering one

Nobody types `@today-7d`. The expression is a **wire format**, not
something to put in front of a user, so the control is a server-rendered
list of presets whose option values *are* the expressions:

```html
<select class="hc-select" name="f-ship-from"
        data-hx-get="/orders/filters/ship-from"
        data-hx-target="closest .hc-field" data-hx-swap="outerHTML">
  <option value="">Any</option>
  <option value="@today">Today</option>
  <option value="@week-start" selected>This week</option>
  <option value="@today-7d">Last 7 days</option>
  <option value="custom">Custom date…</option>
</select>
```

The server renders the presets, because it knows which ones suit the
column — "this quarter" belongs on a ledger date, not on a last-login
stamp — and renders the applied one `selected`, so a saved view reopens
showing **This week** rather than a raw expression.

:::danger[Do not render both controls and hide one]
Hidden controls **keep submitting**
([conditional-fields](/hypermedia-components/recipes/conditional-fields/)),
so a hidden date input next to a visible preset select would send
`f-ship-from` twice and leave the server guessing. Choosing **Custom
date…** therefore *re-renders* the field as a date input: one name, one
control, always.
:::

:::caution[An unknown expression is an error]
Answer `400`, or re-ask. Never fall back to the unfiltered list: a
silently dropped condition shows the user *more* data than they asked
for. Same rule, same reason, as an expired condition set.
:::

## Empty results

A list filtered to nothing is a dead end, and the more conditions are
applied the less obvious which one is at fault. Answer the empty grid
with the way out — name the **newest** condition, since it is what the
user just did:

```html
<p role="status">
  No orders match these 4 conditions.
  <a href="/orders?f-ship-from=2026-08-01&f-status=open">Drop “Buyer code”</a>
</p>
```

## Export inherits the conditions

In a business screen "download" means *this question, these columns,
every page* — not the forty rows on screen. The export link is **the
same query in another representation**, with the conditions already on
its href:

```html
<a class="hc-button"
   href="/orders.csv?f-status=open&f-ship-from=@week-start&cols=order&cols=customer&sort=-ship">
  Export 4,873 rows
</a>
```

- **The server renders the href.** Only it knows the canonical form of
  the conditions — including a relative expression, which must travel
  *as the expression* so the export means what the screen means.
- **Columns come along**, resolved the way the grid resolved them
  (URL → user preference → default). An export whose columns differ
  from the screen is a support ticket.
- **The label says how many rows.** An export is a commitment, and the
  number is what distinguishes "this page" from "everything".
- **Page number is dropped** — an export is the whole answer, never
  page 7 of it.

:::caution[Large exports are a job, not a download]
Past the point where a request would time out, answer `202` with a
pointer to the job. A silently truncated export is a wrong answer that
looks like a right one.
:::

## Progressive enhancement

The filter is a real GET form (`action` + `method="get"`): without
JavaScript, Apply navigates to `/items?f-status=…` and the server
renders the full page filtered. The grid itself is server-rendered
HTML — filtering never depends on client JavaScript.

## Accessibility

- Native checkboxes with visible labels (`hc-checkbox-label`) — the
  filter is a plain form; no menu semantics to fake.
- The trigger's `aria-label` names the column and, when filtered, the
  active values — the state is announced, not just tinted.
- Closing the popover on success returns focus to the trigger button
  (native popover behavior).
