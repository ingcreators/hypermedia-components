`hc-multicombobox` is a **multi-select** combobox with a tag-input
control. Selected values render as inline chips inside a single
visual surface, the filter input lives next to them, and the
listbox carries `aria-multiselectable="true"` so it doesn't close
after each pick.

Same architectural primitives as
[`hc-combobox`](/hypermedia-components/components/combobox/) —
WAI-ARIA 1.2 combobox pattern, HTML `popover`, CSS Anchor
Positioning, `aria-activedescendant` for the highlighted option
while DOM focus stays on the input.

## Anatomy

| Part | Required | Purpose |
| --- | --- | --- |
| `hc-multicombobox` | yes | Wrapper; carries `data-name` / `data-allow-create`. |
| `hc-multicombobox__control` | yes | The visual control box (pair it with `hc-input`). |
| `hc-multicombobox__tags` | yes | Empty container the behavior fills with tag chips. |
| `hc-multicombobox__input` | yes | The filter input — `role="combobox"`. |
| `hc-multicombobox__listbox` | yes | The option list — `role="listbox"`. |
| `hc-multicombobox__option` | yes | One per option — `role="option"` + `data-value`. |
| `hc-multicombobox__tag` / `__tag-remove` | generated | A tag chip and its × remove button. |
| `hc-multicombobox__hidden` | generated | Hidden-input container for `data-name` form integration. |
| `hc-multicombobox__empty` | generated | "No matches" placeholder while the filter has no hit. |
| `hc-multicombobox__create` | generated | The synthetic "Add …" option (`data-allow-create`). |

You author the **yes** parts; the *generated* ones are created and
removed by `installMulticombobox()` — never write them yourself. The
empty placeholder's text comes from `data-hc-empty` on the **listbox**
when present, else from the i18n key `multicombobox.empty` (see the
[i18n catalog](/hypermedia-components/fundamentals/i18n/)):

```html
<ul class="hc-multicombobox__listbox" id="lang-list" role="listbox"
    data-hc-empty="No matching language">
```

## What `installMulticombobox()` does

- **ARIA**: `aria-multiselectable="true"` on the listbox,
  `aria-haspopup="listbox"`, `aria-autocomplete="list"`,
  `aria-expanded`, `aria-controls` (if missing),
  `aria-activedescendant` tracking the highlighted option.
- **Anchor binding**: inline `anchor-name` on the input,
  `position-anchor` on the listbox. JS positioning fallback for
  browsers without CSS Anchor Positioning.
- **Seeding**: every option with `aria-selected="true"` at install
  time becomes a tag chip — keeps SSR-pre-selected state trivial.
- **Filtering**: case-insensitive substring on each keystroke;
  `.hc-multicombobox__empty` placeholder when nothing matches.
- **Toggle selection**: click or Enter on a highlighted option
  toggles its selected state. The listbox stays open so several
  picks can be made without reopening.
- **Tag removal**:
  - Click the `×` button on a tag.
  - Press `Backspace` while the input is empty to drop the last
    tag (the standard tag-input convention).
- **Form integration**: when the wrapper has `data-name="X"`, the
  behavior writes one `<input type="hidden" name="X" value="…">`
  per selected value inside the wrapper. The form serialises like
  a native `<select multiple name="X">`.
- **Events**: every state change dispatches
  `hc:multicomboboxchange` on the input with
  `detail.{values, added, removed, input}`.

## Keyboard

| Key | Action |
| --- | --- |
| `↓` / `↑` | Open the listbox / move the activedescendant. |
| `Home` / `End` | First / last enabled visible option. |
| `Enter` | Toggle the highlighted option. |
| `Backspace` (input empty) | Remove the last tag. |
| `Escape` | Close the listbox; selections preserved. |
| `Tab` | Close the listbox; normal tab order. |

## Form integration

Set `data-name` on the wrapper for native form serialisation:

```html
<form action="/save" method="post">
  <div class="hc-multicombobox" data-name="languages">…</div>
  <button class="hc-button">Save</button>
</form>
```

Submits as `languages=js&languages=ts&languages=py` — the same shape
a native `<select multiple name="languages">` would produce. PHP /
Rails / Python frameworks parse this without configuration.

## htmx usage

The change event carries the full state, so an htmx swap on every
edit is one trigger declaration:

```html
<div class="hc-multicombobox"
     data-name="languages"
     data-hx-post="/profile/languages"
     data-hx-trigger="hc:multicomboboxchange from:closest .hc-multicombobox"
     data-hx-include="this"
     data-hx-target="#status">
  …
</div>
```

The server persists the values and returns a small confirmation
fragment for `#status` (a "Saved" note, a validation message) — the
control itself is **not** re-rendered; its tags and hidden inputs are
client state.

**Async options** — to load the option list from the server, swap the
listbox's children instead: the behavior reads options live from the
DOM, so swapped-in rows filter, highlight, and toggle like static ones.

```html
<input class="hc-multicombobox__input" type="text" name="q"
       role="combobox" aria-controls="lang-list" aria-label="Languages"
       data-hx-get="/languages/options"
       data-hx-trigger="input changed delay:300ms"
       data-hx-target="#lang-list" data-hx-swap="innerHTML">
```

The server returns only
`<li class="hc-multicombobox__option" role="option" data-value="…">`
rows matching the typed `q`.

## Creatable

Add `data-allow-create` to let users add tags that aren't in the list. When
the typed text has no exact match, a synthetic **"Add …"** option appears;
choosing it (click or <kbd>Enter</kbd>) creates a tag from the raw text and
fires `hc:multicomboboxchange` with the new value in `added`.

```html
<div class="hc-multicombobox" data-name="tags" data-allow-create>…</div>
```

The created tag's label is the value itself, and a hidden `name` input is
added like any other tag. The option label is translatable via the
[i18n catalog](/hypermedia-components/fundamentals/i18n/) (`multicombobox.create`).

## Rich options

for the tag's label and the matched value, and **`data-search`** for the
filter haystack (aliases/keywords), so the rich markup's text doesn't pollute
either:

## Accessibility

- DOM focus stays on the input so the type-ahead anchor is
  consistent — `aria-activedescendant` moves the *highlight*, not
  the focus.
- Each tag is a real focusable button with `aria-label="Remove …"`
  so screen-reader users can land on it and trigger removal.
- Mark unavailable rows with `aria-disabled="true"` rather than
  `disabled` (`<li>` is not a form control).
- The visible activedescendant highlight uses
  `--hc-color-focus-ring` and follows `data-color` themes.

## Out of scope (MVP)

- **Drag-to-reorder** tags.
- **Async option loading** — the docs above show the htmx swap
  pattern; a built-in debounce / cancel helper is not bundled.
