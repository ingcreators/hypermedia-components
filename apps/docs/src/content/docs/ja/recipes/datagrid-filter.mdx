スプレッドシート流の列ごとのフィルタを、ハイパーメディアのまま:
ヘッダーセルのフィルタボタンが
[filter-popover](/hypermedia-components/ja/recipes/filter-popover/)
のシェルを開き、コントロールの名前は **`f-<col>`** で名前空間化されて
います。**Apply** が `f-status=` の繰り返しパラメータ付きでグリッド
URL を GET し、サーバーが
[データグリッド](/hypermedia-components/ja/components/datagrid/)全体を
フィルタ済みで再レンダリングします。クライアント側のフィルタリングは
ありません: 往復 1 回、状態のずれゼロ、印刷やエクスポートは画面と
一致します。新規 JavaScript ゼロ。
[バージョニングポリシー](/hypermedia-components/ja/reference/versioning/)の
対象です。

:::tip[スキャフォールド]
```sh
npx @hypermedia-components/cli add datagrid-filter
npx @hypermedia-components/cli validate page.html
```
`recipe.html`・`expanded.html` と機械検査される
[サーバー契約](https://github.com/ingcreators/hypermedia-components/blob/main/recipes/datagrid-filter/contract.md)が入ります。
:::

## ライブデモ

Status ヘッダーの **Filter** を開き、ステータスをいくつかチェックして
**Apply** — サーバーは一致する行だけで応答し、トリガーは
`data-filtered`(primary バリアント、アクティブな値を並べた
`aria-label`)で戻り、ポップオーバーのチェック状態はアウトオブバンドで
追随します。全部外すと、パラメータなしブランチが全件リストを返すのが
見られます。

## マークアップ

```html
<div class="hc-datagrid" id="items-grid">
  <!-- サーバーが描画: .hc-datagrid__scroll > table。Status ヘッダー
       セルがフィルタトリガーを持ちます -->
  <!--
  <th class="hc-datagrid__headcell" scope="col">
    Status
    <button class="hc-button" data-variant="ghost" data-size="sm"
            type="button" id="filter-status-trigger"
            popovertarget="filter-status-popover"
            aria-label="Filter Status">Filter</button>
  </th>
  -->
</div>

<div id="filter-status-popover" class="hc-popover" popover>
  <form id="filter-status-form" action="/items" method="get"
        data-hx-get="/items"
        data-hx-target="#items-grid"
        data-hc-close-popover-on-success>
    <fieldset class="hc-popover__body" id="filter-status-fields">
      <label class="hc-checkbox-label">
        <input class="hc-checkbox" type="checkbox" name="f-status" value="active">
        Active
      </label>
      <!-- …個別の値ごとにチェックボックスを 1 つずつ… -->
    </fieldset>
    <footer class="hc-popover__footer">
      <button class="hc-button" type="submit" data-variant="primary">Apply</button>
    </footer>
  </form>
</div>
```

フォームは filter-popover のシェルです —
`data-hc-close-popover-on-success`(`installClosePopover()`、
自動インストール)がどの 2xx でも閉じます。コントロールはすべて列の
名前空間付き名(`f-status`)を共有するため、Apply は `f-status=` の
繰り返しパラメータをシリアライズし、フォームは**グリッドラッパー**
(`innerHTML` デフォルト)をターゲットにします — トリガーのフィルタ
状態はヘッダーに住んでいるので、ヘッダーと行は必ず一緒に変わります。

## サーバーレスポンス契約

`GET /items?f-status=active&…`:

| ケース | レスポンス (200) |
| --- | --- |
| いずれかの `f-<col>` あり | 一致する行だけのグリッドフラグメント。ヘッダーのトリガーは **`data-filtered`** とアクティブな値を並べた `aria-label` で描画。加えてフォームの**フィールドセット**の OOB `outerHTML` 再レンダリング(チェック状態が一致。フォーム自体は決して置き換えない — `data-hc-close-popover-on-success` を運んでおりリクエストを生き延びる必要があります) |
| `f-<col>` が空/なし | フィルタなしのグリッド — 全部外した Apply はパラメータを一切送らないのでここに落ちます。トリガーは素のまま |
| 未知の値 | 無視(サーバーがスキーマ)。認識できるものが残らなければフィルタなし |

**フィルタは列をまたいで合成されます**: 各列のフォームは*他の*列の
アクティブなフィルタをサーバーが描画した隠し `f-<col>` 入力として
運ぶため、あるフィルタの適用が残りを保持します。クエリ文字列が
フィルタ状態の全体です —
[saved-views](/hypermedia-components/ja/recipes/saved-views/) で名前を
付ければワンクリックで呼び出せ、ページリンクは `f-<col>` パラメータを
持ち回るので
[ページング](/hypermedia-components/ja/recipes/datagrid-pager/)も
フィルタを保持します。

## 適用中条件バー

列のポップオーバーは条件を**作る**ための入口で、作った条件を**探す**
手段としては不便です。幅の広いグリッドでは列が画面外にあるかもしれず、
そもそも列に属さない条件も多くあります。そこでレスポンスは
[`hc-filterbar`](/hypermedia-components/ja/components/filterbar/) も
描画します — クエリストリング全体の読み出しであり、その編集面です。

| 要素 | サーバーが描画するもの |
| --- | --- |
| 適用中の条件 1 つにつき `.hc-filterbar__item` 1 つ | 追加順を保持しているならその順、なければ列順 |
| `__label` / `__op` / `__value` | 項目のラベル、演算子、そして**要約された**値 — 複数値なら `3 values` |
| チップの `popovertarget` | **その条件だけ**を持つエディタ。値が入った状態で、同じ `f-<col>` を送信 |
| `__remove` の `href` | 現在の URL から**そのパラメータだけ**を除いたもの |
| `__clear` の `href` | `f-` パラメータをすべて除いた URL — ソート・列・ページサイズは残る |

バーはグリッドのフラグメントと一緒に届くので、1 回のレスポンスで行・
ヘッダーのトリガー・バーが揃って更新されます。

**削除はナビゲーションです。**`__remove` と `__clear` は実リンクなので、
条件を外す操作は JavaScript なしでも動き、共有でき、**戻るで条件が
戻ります**。`data-hx-get` を足せばその場で差し替えられます。href は
no-JS 経路として残ります。

入口が違っても書き込むパラメータは同じです — 列のポップオーバー、
チップのエディタ、手で打った URL は、1 つのワイヤへの 3 つの扉です。

## 相対日付

保存ビューの実体は保存されたクエリストリングです。そこに絶対日付を
入れると、そのビューは**翌日には間違い**になります。月曜に保存した
「今週出荷」は、次の月曜には先週を意味します。そして業務で保存される
ビューの相当数が時間軸を含みます。

そこで条件の値には**式**を許し、保存されるのは式そのものにします。

```text
?f-ship=@week-start..@week-end
?f-ordered=@today-7d..@today
```

`@today`、`@week-start` / `@week-end`、`@month-start` / `@month-end`、
`@quarter-*`、`@year-*`、および**すべての**アンカーからのオフセット
（`@today-7d`、`@month-end-1m`＝前月末、単位は `d` / `w` / `m` / `y`）。

**期間**アンカーのオフセットは、期間をずらしてから境界を取ります。
`@month-end-1m` は*1 か月前の月の末日*であって、*今月末から 1 か月引いた
日*ではありません。意味として通じるのは前者だけで、2 月で破綻しないのも
前者だけです。

月・年の加減算は**クランプ**します。3 月 31 日の 1 か月前は 2 月 28 日で
あって 3 月 3 日ではありません。桁あふれさせると、フィルタが黙って
1 か月ぶん広がります。

**解決するのはサーバーで、クライアントではありません。**ブラウザで
解決すると、ブラウザの時計とタイムゾーンが答えに混入し、同じビューを
開いた 2 人が別の行を見ることになります。1 リクエスト内のすべての条件は
**同じ瞬間**に対して解決してください。深夜のリクエストが 2 日にまたがり
ます。

**絶対値は ISO のまま**にします — `2026-08-01` であって
`01/08/2026` ではありません。ロケール書式の日付が保存ビューに入ると、
同僚ごとに別の日を意味します。現地化は
[`<time data-hc-time>`](/hypermedia-components/ja/fundamentals/i18n/)
で**出力時**に行い、ワイヤでは行いません。

**バーには両方**を表示します。

```html
<span class="hc-filterbar__value">start of this week (2026-08-10)</span>
```

どちらか一方では条件が推測になります。文言だけではどの行が入るのかが
分からず、日付だけでは明日ずれることが分かりません。

### どうやって入力するか

`@today-7d` を手で打つ人はいません。式は**ワイヤ形式**であってユーザーに
見せるものではないので、コントロールはサーバーが描画するプリセットの
一覧で、**option の値が式そのもの**です。

```html
<select class="hc-select" name="f-ship"
        data-hx-get="/orders/filters/ship"
        data-hx-target="closest .hc-field" data-hx-swap="outerHTML">
  <option value="">指定なし</option>
  <option value="@today..@today">今日</option>
  <option value="@week-start..@week-end" selected>今週</option>
  <option value="@today-7d..@today">過去 7 日</option>
  <option value="custom-dates">期間を指定…</option>
</select>
```

プリセットをサーバーが描画するのは、その列にどれが適切かを知っているのが
サーバーだからです（「今四半期」は伝票日付には合いますが、最終ログイン
日時には合いません）。適用中のものを `selected` で描画するので、保存
ビューを開き直したとき生の式ではなく**今週**と表示されます。

プリセットは「よく使う答え」しか持てず、「45 日前」は表現できません。
そこで「日付を指定…」側に**コンポーザ**（数値＋単位）を用意します。
その入力欄には条件の名前を**あえて付けません**。開いている間は
`f-ship` を名乗るコントロールが存在せず、まだ何も選ばれていない、
という状態が正直に表現されます。**Use** を押すとサーバーが式を組み立て、
フィールドは通常の select に戻り、組み立てた値が `45 days ago` という
ラベル付きの selected な option として加わります。

式の正準形はサーバーの持ち物なので、組み立てるのもサーバーです。解決を
サーバーが担うのと同じ理由です。

:::danger[相対式を日付入力に入れてはいけません]
プリセットに無い式も式です。**selected な option** として描画してください。
`<input type="date" value="@today-45d">` にすると、ブラウザは空欄を表示し、
次の送信で条件が失われます。日付コントロールに入れてよいのは絶対値
(ISO) だけです。
:::

:::danger[両方描画して片方を隠してはいけません]
隠したコントロールも**送信され続けます**
([conditional-fields](/hypermedia-components/ja/recipes/conditional-fields/))。
プリセットの select の隣に日付入力を隠して置くと、`f-ship` が
2 回送られ、サーバーはどちらの意図か推測することになります。
**期間を指定…** を選んだときはフィールドを*再描画*してください。
名前 1 つにつきコントロールは常に 1 つです。
:::

:::caution[知らない式はエラーです]
`400` を返すか、入力を求め直してください。絞り込みなしの一覧に落とすのは
禁止です。黙って落とされた条件は、ユーザーが求めた**以上の**データを
見せます。期限切れの条件セットと同じ規則、同じ理由です。
:::

## 日付の範囲

日付の絞り込みは**期間**であり、期間は 1 つの条件です。バーのチップは
1 つ、外す操作も 1 つ、保存ビューが持つ値も 1 つ。だからワイヤも
パラメータ 1 つで運びます。

```text
?f-ship=2026-07-01..2026-07-31            絶対
?f-ship=@month-start-1m..@month-end-1m    相対（両端）
?f-ship=@month-start-1m..2026-07-15       混在 — 実務ではこれが普通
?f-ship=@month-start..                    片側開き
```

`f-ship-from` ＋ `f-ship-to` にしないのは、**プリセットが 1 つの
コントロールで両端を決められなければならない**からです。「先月」は
1 回の選択であり、2 パラメータで表そうとすると隠しフィールドが要り、
隠したコントロールは送信され続けます。名前 1 つにコントロール 1 つ、
プリセットとカスタムの切り替えと同じ規則です。

両端はそれぞれ独立に解決されるので、混在の範囲に特別扱いは要りません。

### コントロールは 2 つ、パラメータは 1 つ

絶対日付の両端は 2 つの日付入力に置きます。JavaScript が無い経路でも
そのまま送信できるよう、**実際の name** を持たせます。

```html
<div class="hc-cluster" role="group" aria-labelledby="ship-label"
     data-hc-range="f-ship">
  <input class="hc-input" type="date" name="f-ship-from" aria-label="Ship date from">
  <span aria-hidden="true">–</span>
  <input class="hc-input" type="date" name="f-ship-to" aria-label="Ship date to">
</div>
```

`installRangeValue()` が `formdata` イベント — htmx もネイティブ送信も
発火させるフック — でこの 2 つを `f-ship=A..B` に束ねます。どちらの端を
直しても往復は発生せず、バーのチップは 1 つのままです。
**サーバーは両方の形を受け付けます**。ビヘイビアが動かなかった経路では
ペアが届くからです。

両端が空なら**パラメータ自体を送りません**。片側だけ空ならそのまま
片側開き（`A..`、`..B`）です。

:::danger[`from > to` は入れ替えず拒否します]
端を黙って並べ替えるのは、*書かれたものと違う条件を実行する*ことです。
このパターンが防ごうとしている失敗そのものです。ビヘイビアは 2 つ目の
コントロールにネイティブの検証メッセージを立てるので、ブラウザが送信を
止め、htmx はリクエストを発行しません。URL は誰でも打てるので、
**サーバーも `400` で拒否します**。
:::

:::caution[クエリストリングの `+` は空白です]
`@today+30d` は `@today 30d` として届きます。リンクは文字列連結ではなく
`URLSearchParams` で組み立ててください。
:::

## 結果が 0 件のとき

条件で絞り切って 0 件になった一覧は行き止まりで、条件が増えるほど
どれが原因か分かりにくくなります。空のグリッドには逃げ道を添えて
ください。名指しするのは**いちばん新しい**条件です。ユーザーが直前に
やったことだからです。

```html
<p role="status">
  この 4 条件に一致する受注はありません。
  <a href="/orders?f-ship-from=2026-08-01&f-status=open">「発注者コード」を外す</a>
</p>
```

## エクスポートは条件を継承する

業務画面の「ダウンロード」は*この問い・この列・全ページ*を意味します。
画面に出ている 40 行ではありません。エクスポートのリンクは**同じクエリの
別表現**であり、href には条件が既に載っています。

```html
<a class="hc-button"
   href="/orders.csv?f-status=open&f-ship-from=@week-start&cols=order&cols=customer&sort=-ship">
  4,873 件をエクスポート
</a>
```

- **href を描画するのはサーバー**です。条件の正準形を知っているのは
  サーバーだけで、相対式は**式のまま**運ぶ必要があります。そうして
  初めてエクスポートが画面と同じ意味になります。
- **列も一緒に運びます。**グリッドと同じ解決順序（URL → ユーザー設定 →
  既定）で確定した `cols=` を送ってください。画面と列が違うエクスポートは
  問い合わせの元です。
- **ラベルに件数を出します。**エクスポートは約束です。「このページ」と
  「全件」を区別できるのは数字だけです。
- **ページ番号だけは落とします。**エクスポートは答え全体であって、その
  7 ページ目ではありません。

:::caution[大量のエクスポートはダウンロードではなくジョブです]
リクエストがタイムアウトする規模を超えたら、`202` とジョブへのポインタを
返してください。黙って打ち切られたエクスポートは、正しく見える誤答です。
:::

## プログレッシブエンハンスメント

フィルタは本物の GET フォームです(`action` + `method="get"`):
JavaScript なしでは Apply は `/items?f-status=…` へ遷移し、サーバーが
フィルタ済みのフルページを描画します。グリッド自体がサーバー描画の
HTML なので、フィルタリングがクライアント JavaScript に依存することは
ありません。

## アクセシビリティ

- 可視ラベル付きのネイティブチェックボックス(`hc-checkbox-label`)—
  フィルタはただのフォームで、メニューセマンティクスの偽装は
  ありません。
- トリガーの `aria-label` は列名と、フィルタ中はアクティブな値を
  伝えます — 状態は色だけでなく読み上げられます。
- 成功時にポップオーバーが閉じるとフォーカスはトリガーボタンに
  戻ります(ネイティブ popover の挙動)。
